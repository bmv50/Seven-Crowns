# MAX: текстовый транспорт (закрытый MVP)

Один процесс `bot.main` обслуживает Telegram polling и MAX webhook. У них общие
`GameLoop`, `world`, `chars` и PostgreSQL. MAX-аккаунт получает отдельный
внутренний uid; существующий Telegram-герой автоматически не переносится.

## Включение

По умолчанию `MAX_ENABLED=0`, поэтому текущий Telegram-сервер не меняет
поведения. Перед включением нужны резервная копия БД, публичный домен с HTTPS
на порту 443 и reverse proxy на `http://127.0.0.1:8080/max/webhook` (при ином
`MAX_WEBHOOK_PORT` — соответствующий порт). Прокси должен передавать заголовок
`X-Max-Bot-Api-Secret` без изменений. Docker Compose публикует внутренний порт
бота только на loopback хоста, не в публичную сеть.

В секретах сервера задайте `MAX_ENABLED=1`, `MAX_BOT_TOKEN`, случайный
`MAX_WEBHOOK_SECRET` (5–256 символов из `A-Z a-z 0-9 _ -`) и при необходимости
`MAX_WEBHOOK_PORT`. Не вписывайте значения в Git и не отправляйте токен в чат.
Для Docker Compose используйте опциональный `docker-compose.max.yml` вместе с
основным файлом: `docker compose -f docker-compose.yml -f docker-compose.max.yml
up -d --build`; обычный Telegram-деплой не публикует порт. Затем
зарегистрируйте webhook вызовом `POST https://platform-api2.max.ru/subscriptions`
с заголовком `Authorization: <MAX_BOT_TOKEN>` и телом:

```json
{
  "url": "https://ВАШ-ДОМЕН/max/webhook",
  "update_types": ["bot_started", "message_created"],
  "secret": "ЗНАЧЕНИЕ_MAX_WEBHOOK_SECRET"
}
```

Подписку не создаёт сам игровой процесс: запуск кода без публичного HTTPS и
секрета не должен менять настройки действующего MAX-бота. После регистрации
проверьте `/start` в личном диалоге. Групповые чаты и каналы игнорируются.

## Команды MVP

`/start` показывает расы и классы. `/create <раса> <класс> <имя>` создаёт
отдельного MAX-героя. Затем доступны `осмотр`, стороны света, `характеристики`,
`инвентарь`, `умения`, `задания`, `удар [враг]`, `cast [умение]`, `bash`, `flee`,
`get`, `use`, `wield`, `drop`, `/respawn` и `/help`. Для сюжетного продвижения:
`/npcs`, `/talk <код NPC>`, `/say <текст>`, `/accept <код задания>`,
`/turnin <код задания>`, `/choose <код> <вариант>` → `/confirm`. Для торговли:
`/shop [код торговца]`, `/buy <код предмета>`, `/sell [код предмета]`.
Поручения NPC: `/errand [код NPC]`, `/erraccept`, `/errturnin`, `/errabandon`.
У кузнеца доступен `/repair` с подтверждением `/repair confirm`.
У учителя: `/train` показывает доступные умения, `/learn <код умения>` учит
их за золото. `/skills` показывает коды изученных умений;
`/loadout <код>` добавляет или убирает умение из боевой панели,
`/preset save <1–3>` и `/preset load <1–3>` сохраняют и загружают набор.
С 3-го уровня `/group` показывает состав и ID игроков рядом;
`/pinvite <ID>` приглашает игрока в комнате, `/paccept` и `/pdecline`
отвечают на приглашение, `/pleave` выводит из группы, `/party <текст>`
отправляет сообщение группе. Приглашения и состав общие для Telegram и MAX.
С PostgreSQL каждое изменение группы записывается сразу в `kv_state`
(ключ `parties`) и восстанавливается при перезапуске. Ошибка записи отменяет
подтверждение действия. Удалённые персонажи исключаются при восстановлении;
при уходе или удалении лидера его приглашения аннулируются.
Коды показаны в ответах NPC и лавки. Выбор по квесту требует отдельного
подтверждения. Проверки доступности квеста, поручения, присутствия NPC,
ассортимента и продажи торговцу общие для Telegram и MAX.
С 10-го уровня доступны общие гильдии: `/guild`, `/gcreate <название>`,
`/ginvite <ID игрока в комнате>`, `/gaccept`, `/gdecline`, `/gleave`,
`/gchat <текст>`. Управление составом: `/gpromote <ID>`, `/gdemote <ID>`,
`/gkick <ID>`; права и старшинство проверяются по актуальному составу в БД.
Банк: `/gbank`, `/gdeposit <бронза>`, `/gwithdraw <бронза>`,
`/gdeposititem <код>` и `/gwithdrawitem <код>`. Суммы задаются в бронзе:
100 бронзовых = 1 серебряная, 10000 бронзовых = 1 золотая.
Состав, ранги, лидерство и приглашения сохраняются транзакционно; сбой БД
не подтверждает вступление/выход. При уходе лидера преемник выбирается по
рангу, последняя гильдия удаляется после опустошения банка. Сброс героя убирает его членство
и приглашение в той же транзакции. Повтор денежного события не списывает
средства снова. Это текстовый интерфейс; живой плейтест MAX ещё необходим.
Базовый бой, награды, перемещение и сохранение используют то же игровое ядро.
С 12-го уровня в комнате с банком/аукционом доступны `/auction [страница]`,
`/alist` (коды и цены), `/alist <код предмета>`, `/abuy <ID лота>` и
`/acancel <ID лота>`. Витрина общая с Telegram, по 8 лотов на страницу.
Выставляется один экземпляр по общей цене база ×2, комиссия продавца 5%,
не более 10 активных лотов на героя. Квестовые предметы не продаются;
торговля во время боя и после смерти заблокирована. Покупка, выручка,
предмет и комиссия фиксируются одной транзакцией без повторного списания.
При сбросе героя лоты снимаются атомарно, предметы возвращаются старому
герою до мягкого удаления (их можно вернуть восстановлением, но не новым
персонажем). Онлайн-продавец MAX получает сообщение о продаже; оффлайн-push
MAX пока не добавлен, выручка всё равно зачисляется сразу.

Событие сначала попадает в `max_inbox` в PostgreSQL, после чего webhook
возвращает 200. Воркер отмечает событие `processing` до изменения мира, чтобы
повтор MAX не выполнил действие второй раз. После успешной обработки остаётся
`done`, при ошибке — `failed`; текст удаляется. При падении процесса после
`processing` действие может быть потеряно, но не повторяется автоматически:
игрок может отправить команду заново. Проверка зависших событий:

```sql
SELECT status, count(*) FROM max_inbox GROUP BY status;
SELECT event_key, received_at FROM max_inbox WHERE status IN ('processing','failed');
```

## До публичного запуска MAX ещё нужно

- Вынести остальные Telegram-кнопочные игровые операции в общий прикладной слой:
  карта, настройки. Диалог, сюжетные квесты, поручения,
  покупка, продажа, ремонт, обучение, группа, гильдия и аукцион доступны текстом в MAX,
  но требуют живого плейтеста перед публичным запуском.
- Добавить MAX-кнопки, очередь исходящих уведомлений, консолидацию боевых
  сообщений и полноценный retry доставки без повторения игрового действия.
- Проверить нагрузку и реальные webhook/отправку в тестовом диалоге, включая
  рестарт в середине боя, дубли событий и задержки API.
- Отдельно спроектировать подтверждённую привязку Telegram↔MAX и политику
  конфликта двух уже созданных персонажей.

Официальные ограничения: [подписка/webhook](https://dev.max.ru/docs-api/methods/POST/subscriptions),
[отправка сообщений](https://dev.max.ru/docs-api/methods/POST/messages).
